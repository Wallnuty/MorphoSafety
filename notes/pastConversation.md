Research framing established this session
Goal: evolve/optimize robot morphology to study safety improvement. Considering MPC instead of/alongside RL because RL training is slow. Key tension surfaced: RL measures learnability, MPC measures capability ceiling under full observability (vs RL's lidar-only) — these are different claims, not interchangeable. Recommended plan: use MPC (MPPI) for the cheap evolutionary inner loop, then RL-validate top-k finalists.

Hardware/performance conclusions (measured, not guessed)
Laptop (RTX 4050, 6GiB/~3.6 usable, 7.6GiB WSL RAM): throughput saturates ~256 envs (8017 env-steps/s); 1024 envs works (10463 steps/s, 979MiB peak VRAM, 2.5GiB RAM headroom) but compiles in 264s vs 46s at 256 — compile time is XLA-bound, not memory-bound. 2048 envs gets host-RAM OOM-killed (confirmed via dmesg, not a silent success). 12GB RAM would only unlock 2048 envs for ~10-15% more throughput at ~12min compile — not worth it.
Startup CUDA OOM messages = benign XLA preallocation backoff (0.75→0.9× retry cascade). Cosmetic; real usable VRAM is ~3.6GiB not the reported 6GiB. XLA_PYTHON_CLIENT_MEM_FRACTION=0.60 silences it.
"overflow encountered in cast" warning = upstream MJX cosmetic bug (collision_convex.py:812, float64 sentinel under x64-disabled JAX). Harmless, don't enable x64 to fix it.
Full run wall-clock (current defaults, 5M steps, num_evals=10): ~17.6min training + ~17.3min eval ≈ 35min total. Eval is fixed-cost regardless of training budget (episode_length × num_eval_envs × num_eval_episodes = 320k steps/eval × 10 evals = 3.2M steps, comparable to the 5M training budget).
Cluster (uni cluster, 3 partitions): bigbatch (RTX 3090, 24GB, 128GB RAM) is the right partition, NOT biggpu. RTX 3090 (~35.6 TFLOPS, Ampere) is faster than biggpu's Quadro RTX8000 (~16.3 TFLOPS, Turing) despite smaller VRAM — your workload never approaches even the 3090's memory. stampede's GTX1060 is slower than your own laptop GPU (~4.4 TFLOPS) — verify it isn't too old for jax 0.10.2/jaxlib (Pascal sm_61; check jax.devices() doesn't error on a stampede node). No InfiniBand/MPI needed — use --array + --gres=gpu:1, ignore switch topology. Compile cache should live on shared storage ($HOME, not node-local /tmp), and should be warmed by one serial job first before launching a big array to avoid concurrent-write races on the same cache entries; cluster CPUs (2012-era Xeon E5-2680) compile slower than your laptop, so cold compiles there could be 10+ min.
MPC direction (discussed, not implemented)
Recommended: MPPI, spline-parameterized action knots (not per-timestep), feasibility-first elite selection (rank by cost ≤ budget first, reward second — analogous to CRPO's switching rule, keeps MPC and RL constraint-comparable). Ruled out gradient-based MPC (iLQR/DDP/SQP) — the cost function is a discontinuous indicator (sum(collisions) + sum(hazard_distances <= 0.2)), nothing to linearize. Ruled out learned-model approaches (PETS/TD-MPC2/Dreamer) — you already have the true model, and learning one reintroduces training variance.

Three caveats flagged for the MPC design, none yet acted on:

Observability confound — MPC would plan on true state, RL only sees lidar; must either state this asymmetry explicitly or restrict MPC to lidar-derived hazard estimates.
Indicator costs are sparse for planning — should plan with a shaped surrogate (signed distance to the 0.2m hazard boundary) but score/report with the true indicator, kept separate.
Goal resampling mid-horizon — a rollout that crosses a goal-reached event plans through a random teleport; suggested fix is to terminate rollouts at goal contact with a terminal bonus, consistent with the just-fixed +1.0 goal bonus in the real env.
